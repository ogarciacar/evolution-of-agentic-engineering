SOURCE

AI Evals: A Hands-On Guide for Product Teams

View source →
OBSERVED

Torres defines AI evals as methods for measuring whether an AI product or workflow is performing well, and describes them as a feedback loop that can help teams maintain quality and catch issues before they reach users.

For the customer-facing Interview Coach, Torres says she released the product in beta to obtain traces, reviewed hundreds of cases, logged mistakes, and categorized those errors into candidates for evals. She describes a trace as including user input, system prompts, tool calls, intermediate steps, and final LLM responses.

The article describes four common eval types: golden datasets, code assertions, LLM-as-a-Judge, and customer feedback. Torres prefers deterministic code assertions when possible because they are fast and cheap, and uses LLM-as-a-Judge when the error requires judgment because those evals are more expensive and require additional alignment work.

Torres describes combining a cheap code assertion with an LLM-as-a-Judge so only cases that cross a structural threshold are sent to the judge, reducing how often the more expensive evaluation must run.

The article recommends establishing a baseline, changing a prompt, context, model, decomposition, or orchestration pattern, running the same inputs through the variant, applying the evals, and comparing the new scores with the baseline. Torres says this process may require multiple experiment variants before an improvement is found.

For customer-facing products, Torres describes a Python test harness that calls the LLM service for each input, logs outputs, transforms those outputs into the inputs required by each eval, runs the evals, and scores the full run. She also describes using Claude Code sub-agents and Python scripts to run evals for personal workflows.

The article ends its practical loop by instructing teams to collect a baseline, design and run an experiment, compare the results, and repeat the cycle until the desired outcome is reached.

INTERPRETATION

The described eval loop provides a concrete mechanism for subjecting variation to Selection. Traces make behavior observable; error analysis and evals turn observed failures into explicit fitness criteria; baseline comparisons provide verification evidence for choosing among prompt, context, model, decomposition, and orchestration variants; evaluation cost influences which checks are run; and repeated error analysis feeds new criteria back into later experiments. Verification, Observability, Economics, and Learning can therefore operate together as a control loop that determines which variants are retained.

MODEL IMPLICATION

REFINES. This refines Selection by making one possible filtering mechanism explicit. Variation in an agentic configuration is not a separate evolutionary stage: variants can be compared against executable evaluation criteria and a baseline. Failures discovered through observation can become new evals for future runs, connecting Verification to Learning as recurring selection pressure.

Epistemic boundaries

What this does not establish

  • The source does not establish operation of hundreds or thousands of coding agents, or any particular concurrent-agent population.
  • The article is a practitioner guide with examples from the author's own AI products and workflows, not a controlled or independently replicated study of eval systems.
  • The source does not establish that automated evals eliminate human judgment; its process still includes manual error analysis, defining correctness, and aligning LLM judges with human judgment.
  • The source does not establish that eval adoption by itself improves software engineering productivity, quality, or economics at organizational scale.
  • The use of Claude Code sub-agents as an evaluation technique does not by itself establish Cooperation or Specialization in the working model.
  • The source does not establish the model's proposed evolutionary sequence or validate the 1K-agent forcing function.
OPEN QUESTION

At large coding-agent populations, can evaluation remain representative, economical, and sufficiently automated that fitness can be selected without human verification becoming the throughput ceiling?
